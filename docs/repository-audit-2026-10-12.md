# Аудит и следующий этап Lakehouse Ops Platform

Дата: 2026-10-12. Проверены `origin/main` на `1ee43c6` и рабочая ветка `feat/commerce-checkpoint-exit-acceptance` на `53b51ac`. Отличие ветки касается диагностики checkpoint, не перечисленных ниже Spark-преобразований. Это результаты анализа и план, не отчёт об исправлении найденных проблем.

## Решение

Основу проекта сохраняем. Здесь есть работающие преобразования, нормальные границы между хранилищем, вычислениями и управлением, реальные проверки повторной загрузки, доступа и восстановления. Переписывать всё с нуля оснований нет.

Однако продолжать прежним способом, добавляя отдельную команду и runbook на каждый небольшой эксперимент, неэффективно. Получилась сильная операционная лаборатория с недостаточно собранным основным пользовательским сценарием. Наиболее важные следующие изменения: целостность истории клиента при сбое, продолжение обычной загрузки после поздней коррекции, единый рабочий путь и измеренная стоимость его выполнения.

Целевой продукт остаётся локальным воспроизводимым lakehouse для портфолио Data Engineer и изучения эксплуатации Iceberg. Commerce должен стать его основным понятным нагрузочным сценарием. Готовность к многопользовательской промышленной эксплуатации этим аудитом не установлена.

## Как проект работает простыми словами

1. Синтетические заказы, платежи, товары и клиенты попадают в MinIO. Манифест отмечает, что загрузка всех файлов завершена.
2. Spark переносит данные в Iceberg, отделяет некорректные записи, удаляет повторные заказы, строит историю клиентов и выручку по дням.
3. Hive Metastore хранит сведения о таблицах. Trino читает их SQL-запросами из того же хранилища.
4. Python запускает стадии, проверяет результат через Trino и лишь затем сохраняет checkpoint. Отдельный журнал помогает разобраться в незавершённых попытках.
5. Ranger, мониторинг, обслуживание Iceberg и recovery-drills обеспечивают дополнительные эксплуатационные сценарии. ClickHouse остаётся необязательным экспериментом.

В связанных commerce-загрузках вход является **полным снимком**, а не потоком отдельных изменений. Выручку трёх состояний 1000, 1500 и 2200 нельзя складывать в 4700: актуальный результат равен 2200. Для него есть отдельная `gold.commerce_current_daily`; историческая `gold.commerce_daily` хранит результаты по пакетам.

## Сильные стороны, которые стоит сохранить

- Файлы публикуются до манифеста, запись в S3 условная, содержимое связано контрольными суммами. Это реальная защита от частичной загрузки и конфликтующего повтора.
- Обработка платежей и заказов сохраняет reject-данные и сверяет количества. Денежные значения хранятся целыми минимальными единицами.
- Существуют независимые буквальные эталоны выручки и истории, проверки через реальный Spark/Iceberg и Trino, а не только моки успешных ответов.
- План обслуживания Iceberg отделён от исполнения; есть dry-run, проверка snapshot и явное подтверждение опасных действий.
- Локальные блокировки, журнал попыток, ограничение времени Compose-стадий и привязка контейнеров к запуску имеют практический смысл.
- Зависимости и образы зафиксированы; совместимость публичного интерфейса и release-evidence проверяются отдельно. Новые экспериментальные возможности не маскируются выпуском версии на каждый PR.

Доказательства: `ingestion/commerce_s3_landing.py`, `commerce_pipeline.py`, `commerce_run_journal.py`, `iceberg/planner.py`, `iceberg/executor.py` внутри `src/lakehouse_ops`; `jobs/spark`; `tests/integration`; `.github/workflows/ci.yml`; `docs/release-policy.md`.

## Проблемы в порядке важности

### 1. История клиента обновляется двумя коммитами

В `jobs/spark/commerce_customer_scd2.py:204` MERGE закрывает текущую версию, а `:229` отдельный append создаёт следующую. Воспроизведение остановило выполнение после успешного MERGE, до append. Таблица осталась с одной закрытой записью и **нулём текущих записей**. `validate_target` (`:116`) это принял: он ищет больше одной текущей версии, но не отсутствие текущей версии.

Повтор того же пакета успешно восстановил две версии и одну текущую запись. Это подтверждённое окно неконсистентности, а не доказанная безвозвратная потеря данных. Существующие owner-exit проверки в основном прерывают выполнение уже после завершённого gold; этот внутренний переход они не покрывают.

Рекомендация: закрытие старых и публикацию новых версий делать одним Iceberg-коммитом в существующем однописательном режиме. Сначала закрепить воспроизведение тестом. Проверять, что читатель видит целиком старую или новую историю, а не промежуточное состояние.

### 2. Ручная поздняя коррекция не замыкается с обычной очередью

`commerce_linked_acceptance.py:209` публикует поздний пакет в тот же landing. `commerce_history_correction.py:56` намеренно сохраняет старый checkpoint: выполнены только bronze/customer-silver/rebuild, остальные стадии пакета не завершены. После успешного demo остаётся четыре манифеста и три обработанных пакета.

`CommerceBatchPlanner.plan` (`ingestion/commerce_batches.py:86`) вновь выбирает поздний пакет `6ffe8636c50331a7`. Forward-режим SCD2 отклоняет его с `selected customer batch is not newer than current history`, даже после успешного rebuild. Обычный последовательный путь не сможет продвинуться без дополнительного решения. Сам drill честно назван ручным maintenance, но его результат нельзя считать готовым непрерывным сценарием.

Рекомендация: явный путь позднего полного снимка в существующем runner, с корректной историей, защитой актуальной витрины от старого состояния и checkpoint только после всех необходимых стадий. Customer-only maintenance должен иметь отдельную семантику и не оставлять ловушку в обычной очереди. Нельзя просто отметить частично обработанный пакет завершённым ради зелёного теста.

### 3. Тайм-ауты есть не на всём пути

Compose-стадии ограничены, но `commerce_cycle.py:65` ждёт дочерний процесс без общего срока. `cli.py:625` создаёт Trino-клиент без уже реализованного `query_timeout`; его значение по умолчанию в `trino.py:57` равно `None`. Лимит HTTP-запроса и предел числа страниц не равны управляемому бюджету всего запуска.

Это подтверждённый пробел в настройках, не воспроизведённый здесь зависший production-запуск. Нужно провести бюджет времени через обычный runner и scheduled cycle, проверить отмену запроса и судьбу собственного активного контейнера при остановке владельца. Наличие локального журнала не обеспечивает распределённую exactly-once обработку.

### 4. Возможности разнесены по разным маршрутам

Обычный `COMMERCE_STAGES` заканчивается batch-scoped gold. Актуальную витрину добавляет callback специального `commerce_linked_acceptance.py:107`; поздняя история обрабатывается ещё одним отдельным маршрутом. Поэтому прохождение демонстрации не означает, что обычная команда выполняет весь показанный сценарий.

Есть и уже наблюдаемый дрейф дублирования: `local_quality.py` проверяет lock и Compose-конфигурацию, а `commerce_local_check.py` самостоятельно перечисляет похожие проверки без этих двух шагов. Общий механизм должен переиспользоваться, не переписываться в очередной обёртке.

Сейчас в tracked-файлах 60 runbooks, README на 405 строк, Compose на 1741 строку и CI на 1343 строки. За 12 октября в `origin/main` попал 31 коммит; roadmap изменялся в 22 из последних 32 коммитов. Размер сам по себе не дефект. Но вместе с незамкнутым основным сценарием это признак того, что учёт отдельных экспериментов обгоняет сборку продукта.

### 5. Эффективность пока доказана лишь на малом масштабе

Сохранённый, не повторённый в этом аудите полный профиль:

| Заказы | Полный batch-run | Максимальный наблюдённый пик одного Spark-контейнера |
|---|---:|---:|
| 100 | 95,01 с | 1127,75 MiB |
| 1000 | 95,12 с | 1047,32 MiB |

Оба случая имеют только 10 клиентов и 5 товаров. Второй прогон использует прогретый стек. Память всей платформы этим столбцом не измерена. Почти одинаковое время согласуется с существенными постоянными затратами семи последовательных Spark-запусков, но для определения главной причины нужен профиль стадий и повторные измерения.

Полезный результат уже есть: на сохранённом наборе из 1000 заказов медиана четырёх прогретых SQL-чтений витрины составила 41 мс против 115,5 мс для агрегации деталей, при совпадающей выручке. Это ограниченное доказательство пользы витрины, не SLA.

Эксперимент compaction сократил шесть искусственно созданных файлов копии до одного. Время запроса изменилось с 86 до 110 мс, поэтому заявлять ускорение на основании этого эксперимента нельзя.

При аудите обнаружены восемь запущенных Trino workers в семи старых проектах без работающих координаторов этих проектов. Они занимали суммарно примерно **5,85 GiB**; просмотренный worker продолжал безуспешно искать координатор. Это лишняя фактическая нагрузка на ноутбук. В рамках анализа они не останавливались; новые диагностические контейнеры были одноразовыми и завершились.

## План вместо дальнейшего роста обвязки

| Порядок | Законченный результат | Условие приёмки |
|---|---|---|
| 1. Целостность и продолжение | Атомарное обновление SCD2; определённая обработка позднего пакета | Сбой на границах записи не оставляет опубликованную историю без текущей версии. После поздней коррекции следующий обычный пакет завершается, затем runner выходит в idle. Нет дублей, преждевременного checkpoint и отката выручки. |
| 2. Измерены время стадий, память всего стека и Spark, файлы, SQL и восстановление. Выбрано одно узкое место; улучшение показано до/после с неизменными эталонами. |
| 4. Понятная демонстрация и релиз | Заказ → исправление → позднее исправление → сбой → повтор → следующий пакет → SQL-результат | Пользователь может воспроизвести и объяснить сценарий. Обязательный CI зелёный для точного SHA, RC-пакет включает именно этот путь, ограничения и upgrade notes сохранены. Только после этого релиз по действующей политике. |

Перед большими измерениями отдельно остановить подтверждённые старые контейнеры этого проекта, сохранить данные и убрать конкурирующую нагрузку. Не выполнять глобальный Docker prune и не затрагивать другие проекты.

Первый кандидат на оптимизацию после профилирования: проверить, можно ли переиспользовать одну Spark-сессию для нескольких стадий без ухудшения изоляции и восстановления. Альтернативы по измерениям: уменьшить повторные Spark actions, потоково читать landing, ограничить повторное чтение всей истории манифестов. Это гипотезы, не обещания ускорения и не повод переписывать всё заранее.

Не добавлять сейчас Kafka, Kubernetes, ещё один движок, универсальный оркестратор, новые диагностические оболочки или дополнительные релизные схемы без конкретного приёмочного сценария. Существующие Ranger, мониторинг и maintenance сохранить как поддерживаемые дополнительные профили. Не удалять совместимые команды ради косметической чистоты.

У каждого следующего PR должны быть три ясных ответа: что стало лучше для пользователя; каким тестом/замером это доказано; какая сложность добавилась или убралась. Мерой прогресса становятся корректный сквозной сценарий, восстановление и стоимость выполнения, а не число PR и галочек. Пока CI идёт, можно продолжать независимую работу в отдельной ветке; содержание уже проверяемого PR не расширять.
