# Version 1.28.0 release notes

Version `1.28.0` adds the supported commerce workload that was absent from tag
`v1.27.0`. Publication requires the integrated walkthrough and final release
source to pass the existing CI/RC policy. The minor release consolidates the
complete user path; individual benchmarks do not authorize a release.

The candidate brings synthetic customers, products, orders and payments through
MinIO, Spark/Iceberg and Trino using one normal runner. Its complete demonstration
covers load, change, late correction, caught failure, retry, the next ordinary
batch and compute-free idle. Weather, Ranger, observability and maintenance remain
supported; ClickHouse remains an optional experiment.

## Reproduce the supported path

From the checkout, prepare the reviewed images using the main README prerequisites,
then choose a new empty output directory:

```powershell
uv run --frozen python -m lakehouse_ops.commerce_history_correction_demo --output artifacts/commerce-release-demo
```

Current revenue must progress through 1000, 1500 and 2200 captured cents, not sum to
4700. After late customer correction, the three contiguous periods are Alice,
Alice Corrected and Alice Updated, with exactly one current version. The caught
post-batch-gold failure records no checkpoint; only the complete retry records the
fourth. The next ordinary full snapshot records the fifth and reaches idle at
2200 cents with the corrected history unchanged.

Inspect `demo.json` and the retained `acceptance/` report, checkpoint, stage log
and ownership journal after scoped shutdown. The demo removes only its own
containers/empty network and retains named data volumes. It does not leave a live
SQL endpoint, reset a checkpoint, pull/build images during execution or prune Docker.

## Measured cost and its boundaries

The [matched-load report](../runbooks/commerce-pipeline-profile-demo.md) retains
three observations per state. Runner medians exclude service startup and extra
post-run profiling. Every full snapshot completes nine stages, including eight
new Spark processes, with independent input/SQL reconciliation and stable idle.

| Orders | Fresh / warm runner seconds | Fresh / warm sampled stack MiB | Fresh / warm largest Spark peak MiB |
|---:|---:|---:|---:|
| 1000 | 133.485 / 129.117 | 3576.56 / 3672.09 | 998.58 / 1012.85 |
| 10000 | 134.254 / 132.066 | 3686.01 / 3770.93 | 1051.62 / 1024.65 |
| 100000 | 146.325 / 140.143 | 3700.37 / 3877.02 | 1160.06 / 1188.79 |

Fresh means fresh services/catalog with locally available images, not flushed
OS/VM/image caches. Warm retains one prior completed batch, not one shared Spark
session. Stack memory is the sampled simultaneous sum for the owned project;
Spark is per-container cgroup peak, neither host RSS nor a machine capacity bound.
All fifteen commerce/SCD2 current inventories contain 13/24 files in fresh/warm
states; these exclude obsolete snapshots, S3 versions and metadata storage.

The [completed-history report](../runbooks/commerce-pipeline-scale.md) separately
processes ten real chronological full snapshots in each of three 1k-order cohorts.
Current file counts at batches 1/5/10 are 13/57/112; current business revenue does
not accumulate across snapshots. This is ten completed batches, not the separate
1000-pending-manifest planning experiment or arbitrary history depth.

The [recovery observations](../runbooks/commerce-recovery-acceptance.md) retain
three repeats at 1k/10k/100k: retry medians 109.817/111.191/117.820 seconds, with
unchanged canonical rows and physical files, a hash-bound checkpoint only after
success and compute-free idle. This is ordinary batch-scoped input with a caught
post-gold exception, not the full-snapshot correction workload, SIGKILL or failure
inside a commit. Volumes were measured separately, not interleaved for a controlled
cross-volume speedup comparison.

For the same 1000 pending manifests, bounded eight-worker fresh reads reduced
median planning-plus-option resolution from 4.755 to 3.410 seconds (28.3%) over
three alternating pairs. Checksums, selected batch and fresh reads are unchanged.
See the [planning A/B](../runbooks/commerce-selected-source-sync.md) for smaller
queues, raw hashes and the serial/custom-client rollback. This is not a
whole-pipeline speedup; instrumentation timings and heap peaks are separate.
Local measurement reports are not signed RC assets or an SLA.

## Verification and release gate

```powershell
uv run --frozen python -m lakehouse_ops.local_quality
```

This reuses all seven local checks, not live acceptance. Mandatory integration CI
additionally exercises the actual Spark/MinIO/HMS/Trino and supported Ranger/
observability/maintenance paths. Python coverage excludes `jobs/spark`; real
Spark acceptance is a separate requirement, not inferred from that percentage.

The [existing RC procedure](../runbooks/release-candidate.md) packages the complete
commerce report, final checkpoint and SQLite journal from the same workflow run.
Offline verification, byte correlation and retained semantic checks do not rerun
Spark. Constrained verification of all three subject signatures must bind the
final source revision, repository, signer workflow, source ref, issuer and runner
identity. An older main's green CI or signed bundle cannot authorize a later tag.
The existing `1.0.0` core contract/evidence target is not the product release number.

## Upgrade, rollback and limits

No public CLI/JSON major migration is intended: the stable contract stays `1.0.0`.
Keep the existing catalog, named volumes, configuration and completed checkpoints.
Build the checked-in local images before the new demo; compatibility commands and
optional profiles are retained. New commerce tables are created by their normal
jobs, not by dropping existing warehouse tables.

Default generated manifests retain legacy batch semantics. Full-snapshot behavior
requires an explicit declaration when generating a new source identity. Do not
edit a landed manifest, invent a `--source-semantics` flag or acknowledge partial
customer-only work as a completed batch. Late history rebuild requires complete
retained customer silver data. One local writer/checkout owns each workload;
local locks/journals are not distributed coordination across hosts/checkouts.

Arbitrary CDC/deletes, incomplete-retention correction, industrial throughput,
host-cold performance and failure inside an Iceberg transaction are not claimed.
A caught exception, active-stage timeout and forced owner exit after gold each
prove their own boundary, not automatic recovery from every crash.

Rollback to the previous tag preserves warehouse data and restores its supported
weather/operational paths; `v1.27.0` does not provide the new commerce runner.
Do not remove volumes or reset commerce progress to make a downgrade appear safe.
Release publication still requires the final capability/limitation/upgrade notes,
exact-source CI/RC verification and a tag that resolves to that same source.
