# Version 1.10.0 release notes

Version `1.10.0` validates every Trino query baseline against a standalone Draft 2020-12
JSON Schema before performance automation can consume it.

## Capability matrix

| Capability | Status | Evidence |
|---|---|---|
| Trino baseline JSON Schema | Supported | The schema covers corpus identity, query digests, plans, and final metrics |
| Runtime producer validation | Supported | `capture-trino-baseline` validates the complete report before returning success |
| Explicit schema override | Supported | `--schema` selects the reviewed report schema used by automation |
| Stable control-plane verification | Preserved | 17 commands, 32 critical option semantics, and 11 outputs are checked |
| Remaining report schemas | Planned | Four producer reports still use executable producer tests |

## Verification

```bash
uv sync --frozen --dev
uv run ruff check .
uv run lakeops verify-control-plane-contract --contract config/control-plane/contract.json
uv run pytest
docker compose --profile catalog --profile compute --profile query config --quiet
```

## Known limitations

- Four existing public reports do not yet have standalone schemas.
- JSON Schema verifies the type and bounds of each observation, while the existing live
  integration check reconciles the exact checked-in corpus and query count.
- The default schema path assumes commands run from the repository root.
- The baseline remains an observation and does not define latency acceptance thresholds.
- The stack remains a local reference environment, not a capacity-tested,
  highly available, TLS-enabled, or multi-region managed service.

## Upgrade from 1.9.0

No data or infrastructure migration is required. Existing invocations use the default
baseline schema. Automation running elsewhere should pass `--schema` explicitly. The
serialized report is unchanged. Rolling back removes runtime validation.
