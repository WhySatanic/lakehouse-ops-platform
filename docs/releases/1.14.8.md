# Version 1.14.8 release notes

Version `1.14.8` rejects ambiguous duplicate anchor names in public output schemas. The
control-plane gate tracks Draft 2020-12 resource boundaries and requires `$anchor` and
`$dynamicAnchor` names to be unique within each resource before resolving local references.

## Capability matrix

| Capability | Status | Evidence |
|---|---|---|
| Duplicate `$anchor` rejection | Enforced | Repeated static names in one resource fail the gate |
| Duplicate `$dynamicAnchor` rejection | Enforced | Repeated dynamic names in one resource fail the gate |
| Shared anchor namespace | Enforced | Static and dynamic declarations cannot reuse one name |
| Local reference resolution | Preserved | JSON Pointers and anchors must identify bundled targets |
| Stable control-plane verification | Preserved | 17 commands, 36 critical option semantics, and 11 outputs are checked |

## Known limitations

- Anchor uniqueness is scoped per Draft 2020-12 schema resource; separate nested resources
  may intentionally reuse a name.
- Shared remote schema registries remain intentionally unsupported for public outputs.
- The stack remains a local reference environment, not a capacity-tested or multi-region
  managed service.

## Upgrade from 1.14.7

No data, infrastructure, CLI, dependency, or report migration is required. Existing
repository schemas do not contain duplicate anchors. Custom contract extensions must
rename duplicate `$anchor` or `$dynamicAnchor` declarations and update their fragment
references before adopting this version. Rolling back permits ambiguous anchor resolution
again but retains dangling-reference and external-reference rejection.
